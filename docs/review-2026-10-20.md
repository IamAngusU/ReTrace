# Reliability and performance review — 2026-10-20

## Reviewed baseline and scope

This work starts from canonical `IamAngusU/ReTrace` main commit
`ac3ba91793f648a74301594545248dddc09de7e3`, after the native recovery workbench
was merged in PR #1. It covers native photo/video/media scanning, saved
investigations, acquisition preflights, source-path validation, desktop progress
and preview scheduling, release inventories, and the existing test runner.

The review combines source inspection, owned synthetic regression fixtures,
before/after measurements, and independent review of the implementation.
It is not an exhaustive security audit or certification of real-device recovery.
Existing historical Windows validation in [validation.md](validation.md) must
not be treated as execution of the changes in this patch.

## Concrete findings and resulting behavior

| Area | Baseline problem | Resulting behavior |
| --- | --- | --- |
| Format selection | An AVI-only shared scan still assessed ISO/MP4 starts. An earlier unselected MP4 could consume the signature quota and prevent the AVI from being reached. | ISO starts are assessed only when MP4 or MOV is selected. A regression places MP4 before AVI with a one-signature budget. |
| JPEG correctness | A scan containing only stuffed `FF 00` entropy bytes remained partial despite its frame, scan and end markers. | Stuffed bytes count as entropy. Exact ranges and SHA-256 remain checked; structural completeness still does not claim successful image decoding. |
| Parser memory and CPU | Every photo candidate allocated a fresh 64 KiB reader buffer; PNG copies and JPEG entropy search processed bytes individually. | Readers reuse pooled buffers, payload copies use spans, and JPEG marker search uses vectorized span search. Refill, end-of-file, skip and candidate-limit regressions cover the changed reader. |
| Video hashing | Rejected types and large partial containers were hashed before selection and fragment caps, then capped fragments could be hashed again. | Scanners first assess structure and reserve their budgets, then hash only the retained byte range. Public `AssessAt` still returns a fully hashed candidate. |
| Saved-case memory | Case IDs and saves serialized complete JSON copies before enforcing size limits. Loading many small PhotoRec candidates allocated large buffers repeatedly. | Case-ID hashing streams the same compact JSON bytes; serialization stops at the existing 16 MiB limit. Saved-output checks reuse one pooled buffer and bounded direct handle reads. |
| Unavailable source bindings | Live filesystem checks during metadata validation could make an existing case unreadable when its source became a link, directory or unavailable file. | Metadata shape and path containment are validated independently of current source availability. Actual byte access still uses strict source checks; unavailable or changed bindings disable recovery. |
| Acquisition ownership | A receipt-path directory was not rejected before copying; an exclusive output-create failure could be handled as a partial capture owned by this operation. | Invalid inputs, pre-cancellation and occupied receipt paths fail before creating an image. Failure to create the image exclusively propagates without attaching a receipt to someone else's output. |
| Desktop workload | Each worker progress event posted UI work. Rapid selection could start several large preview reads/decodes concurrently. | Each normal job retains one progress snapshot, rendered at a 100 ms cadence. One preview decoder runs at a time; superseded reads observe cancellation between 64 KiB chunks. |
| Package inventory | Every file named `retrace-package.json` was excluded, including unlisted nested files. A linked root inventory could also pass. | Only the root inventory is excluded. All other files must be listed, ordinary, unlinked, and match size/SHA-256. Noncanonical names, Windows case aliases and special files are rejected. |
| Test portability | Windows-only assertions were sometimes counted as successful on other platforms, and a one-character POSIX root threw during path checks. | Real platform-specific checks report explicit skips; portable tests stay active. Root path normalization handles short absolute roots without weakening Windows UNC/device/ADS rejection. |

## Compatibility and data integrity

The public scan/report schema and the stable compact-JSON case-ID format remain
unchanged. Regression tests compare the streaming case ID with the original
`SHA256(JsonSerializer.SerializeToUtf8Bytes(report))` format. Fragment hashes
always cover the final retained range; intermediate un-hashed video assessments
are internal and are never published as scan results.

Opening a valid saved investigation with missing or modified specialist files
now preserves the recorded findings and returns `CanRecover = false`, with
`stored_output_unavailable` or `stored_output_changed`. Previously some such
opens threw an `IOException`. Callers must honor `CanRecover`; the desktop
disables recovery and explains the state. Invalid JSON, schemas, candidate
ranges, and paths escaping a recorded run still fail validation. Actual export
continues to verify its source and candidate hashes independently.

No format repair, fragment stitching, overwrite mode, automatic playback, or
new external dependency is introduced. The distribution remains a Windows
alpha, at the existing version until a separately verified release is prepared.

## Measured performance

The comparison used the original source and isolated carver changes on the
same Linux host with .NET SDK 10.0.402, Release builds and
`DOTNET_TieredCompilation=0`. JPEG, PNG CRC and video cases had two warmups and
five measured runs; rejected-signature allocation measurements had one warmup
and three measured runs. Times below are medians. Fixture setup was outside the
measured operation.

| Controlled operation | Original | Improved | Observed change |
| --- | ---: | ---: | ---: |
| Assess a 16 MiB structural JPEG | 56.4091 ms | 13.8564 ms | 4.07× faster |
| Assess a 16 MiB PNG including CRC work | 100.7125 ms | 53.2914 ms | 1.89× faster |
| Shared scan of a 64 MiB partial video, retained fragment capped to 128 bytes | 87.9838 ms | 43.8695 ms | 2.01× faster |
| Managed allocations for 2,000 rejected PNG signatures | 131,560,360 bytes | 439,912 bytes | 99.67% less allocated memory |

Candidate/source hashes and counts agreed across the comparison. The
stuffed-entropy JPEG's changed state is the intended correctness fix.
These are synthetic measurements with warmed filesystem caches. They do not
establish real-drive speed, end-to-end recovery throughput, or a higher chance
of recovering overwritten data. Managed allocation totals are not peak RSS.

The optional dependency-free benchmark project and reproducible commands are
documented in [benchmarks.md](benchmarks.md). Correctness tests have no elapsed
time gate; the memory regressions use generous bounds for the specific
previously unbounded allocation behavior.

## Validation and remaining release gates

The complete revised C# runner passed **419 assertions** on this Linux host.
The suite counts were: carver 39, video 71, media integration 54, progress 6,
export 26, volume acquisition 25, PhotoRec 32, investigations 87, folders 24,
and Recycle Bin 55. Native-only skips were reported separately. The Python
package verifier passed **14 tests**. The WPF cross-build completed with
**zero warnings and zero errors**, using .NET SDK 10.0.402.

Run the portable checks with .NET 10 and Python 3.11+:

```sh
dotnet run --project tests/ReTrace.Tests/ReTrace.Tests.csproj -c Release
python -m unittest discover -s tests -p 'test_*.py' -v
python scripts/source_manifest.py --verify
```

The C# runner emits the executed suites, assertion count, and explicit
`skipped` reasons as JSON. Python's test runner separately reports unavailable
link/FIFO fixtures. A Linux run does not exercise native Windows file identity,
mandatory sharing/delete protection, junctions, the sparse high-offset suite,
WPF interaction, or the bundled Windows PhotoRec executable.

The WPF application can be compiled on Linux using
`dotnet build src/ReTrace.App/ReTrace.App.csproj -c Release -p:EnableWindowsTargeting=true`.
Compilation is a separate result from actually launching the GUI.

Before release, run the complete Windows tests and the existing native
scan/preview/export, saved-case, folder, Recycle Bin and packaged application
checks described in [release.md](release.md). In particular, exercise rapid
preview selection, UI cancellation, and unreadable native/specialist case
reopening with this patch. Physical-drive acquisition and real damaged-media
recovery were not exercised by this review.

The existing workflow deliberately runs the Windows job only in
`angusu-de/ReTrace`; that policy is preserved. Python inventory regressions are
added to that job. Canonical main's observed Actions run
[39353582010](https://github.com/IamAngusU/ReTrace/actions/runs/39353582010)
reported `startup_failure` with zero jobs. Neither a skipped job nor a startup
failure is evidence of passing hosted CI.

## Further optimization to measure separately

A separately reproduced issue remains in rejected legacy QuickTime parsing:
repeated `wide` atoms can trigger quadratic suffix walks before any candidate
is retained. In instrumented owned fixtures, 64 atoms (512 bytes) required
2,205 parser reads, and 128 atoms (1,024 bytes) required 8,509 reads, in both
standalone and shared scans. Individual box/signature limits still apply, but
rejected parser work needs a cumulative scan budget. The reproduction and
acceptance criteria are tracked in [issue #3](https://github.com/IamAngusU/ReTrace/issues/3).
This issue is not claimed fixed by the current patch.

The PhotoRec monitor enumerates and checks its complete output tree every
100 ms. Large output inventories deserve a separate benchmark before choosing
an incremental inventory design; quota and link protections must remain intact.
Large desktop result sets also rebuild their row collections when filters
change. Those paths were inspected, but this patch makes no measured speed
claim for them. Filesystem-aware reconstruction, fragmented media repair and
additional file families are separate product work.
